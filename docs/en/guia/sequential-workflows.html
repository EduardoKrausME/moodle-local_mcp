Sequential workflows

Stepwise confirmed WRITE workflows.

The MCP server can plan 2–30 Moodle WRITE operations for a single course and guide the client through one confirmation at a time. This behavior is delivered by the Moodle plugin's discovery instructions and an optional MCP Apps Next button, not by ChatGPT memory or custom instructions.

Usage

  1. Call workflow_sequence with action=start, courseid and ordered items containing only title and the existing WRITE tool name.
  2. The response returns an opaque workflow.id and the first step. Generate the arguments only for that step. Call the original tool, including workflow_id and workflow_step=1.
  3. Show the preview and obtain explicit user approval. Reinvoke the same tool with its identical arguments plus confirmation_token. The plugin rejects steps other than the current one and prevents parallel claims.
  4. Verify the created content with the relevant READ tool when available. The successful WRITE result contains workflow progress and an MCP App with a Next button. Clicking it sends a follow-up; it does not authorize a WRITE.
  5. For the next step, call workflow_sequence with action=next, courseid and workflow_id. Prepare a new preview, wait for approval, and repeat. Use action=status to resume or action=cancel to discard a plan.

Example:

{
  "action": "start",
  "courseid": 123,
  "items": [
    {"title": "Discussion forum", "tool": "forum_create_activity"},
    {"title": "Assignment", "tool": "assign_create_activity"}
  ]
}

The specified tools must be installed and exposed by the selected Moodle site; names above are illustrative. The initial plan stores labels and tool names. An official view-completion preview may bind a bounded verification condition; HTML, student data and confirmation tokens are not stored in the workflow.

Safety and interoperability

The same user, client and OAuth connection must access the workflow. The plugin checks the tool name, step number, course context and Moodle capability on each WRITE. An approved WRITE claims a step before execution; a second call cannot claim it. After an exception, the stage is recorded as failed when possible. Only failed moves may be reopened with a fresh preview; unknown executing stages require manual reconciliation.

Workflows expire after seven days. Their state is stored using Moodle's config_plugins API.

MCP Apps-aware clients fetch ui://local-mcp/workflow-next via resources/read and render the Next button after a tracked WRITE succeeds. Clients without UI support still receive structured workflow data and must offer a text-based Next action. The button depends on the MCP client supporting the extension; the server cannot force a native ChatGPT button.

The panel uses the standard MCP Apps JSON-RPC bridge, with legacy ChatGPT fallback, and displays loading, progress, failures and recovery. Buttons send a user message only. They never approve a WRITE. The expected step and generation prevent stale navigation. Hosts without the extension keep the text workflow.

Untracked operations work as before. The plugin does not infer a batch from arbitrary ChatGPT prose: the client must call workflow_sequence(action=start) to activate a server-enforced plan.

Reconciliation of existing settings

workflow_reconcile verifies an immutable server-bound condition captured from the first official set_activity_completion preview. The original preview records intent, not approval. Reconciliation requires separate explicit confirmation and never executes the original operation. The initial verifier accepts automatic view-only completion, without a grade, existing student completion records or active additional rules (including mod_mcp's completioninteractive).

After an independently authorized administrative configuration already exists, check the workflow and call the tool with workflow_id, courseid, expectedstep and expectedgeneration. A mismatch is rejected; there is no force or skip option. Review the preview, then confirm with identical arguments and its token. The server rechecks permissions, policies, connection, context and state, records reconciliation and offers Next. The following operation still requires its own approval.

Legacy plans without a recorded condition, executing stages, grades, academic records, deletions and publishing cannot be reconciled by this tool. Reconciliation is not an alternative way to execute an operation blocked by the client; it only records an existing authorized condition. It never replaces client or Moodle security controls.
